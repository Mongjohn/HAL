## Work amplification chains

1. **Home return:** Activity resumes → frame wait → Watch Next query + full launchable-app queries/labels → saved catalog update if changed → UI app projections + possible artwork-service defaults recomputed. Repeating Home without changes still performs the discovery queries. HAL-03 should eliminate unnecessary refresh triggers before micro-optimizing sorting.
2. **Slideshow advance:** successful fade → `lastDashboardArtwork` preference write → dream's key-agnostic listener increments revision → all revision-keyed JSON/layout/app/settings reads reexecute. HAL-05 should isolate the marker from configuration observers. Cost depends on saved layout size.
3. **HA reconnect:** new session → weather discovery `get_states`, registry reads for followed entities, hourly+daily subscriptions → new session identity restarts mounted player artwork producers → separate artwork fetch/decode per consumer. Some reconnect work is required; HAL-04 and HAL-06 reduce the unrelated multiplier.
4. **Editor read/save:** HTTP request thread parses envelope → main API constructs private/public configuration/revision and layout/catalog JSON → body encoding. `runBlocking` blocks the HTTP worker, not the UI directly; the expensive part is work deliberately dispatched to main. HAL-07 must preserve this distinction.

## Justified separation to retain

- **Filtered live HA subscription versus editor catalog sessions:** the editor needs complete entity/area/template data and login verification; visible dashboard subscription deliberately follows a subset. Do not replace catalog results with incomplete live entities or couple navigation availability to editor discovery.
- **Camera streams, Frigate clips and muted file backgrounds:** different audio focus, buffering, decoder, authentication, error and retention requirements. Share Media3 utilities only where policy is identical. One player for all video would interrupt live cameras or lose warm clip return.
- **MainActivity and cold DreamService:** independent Android lifecycles are required. Share data/resources, not Activity instances or Compose views.
- **Artwork and camera DreamServices:** distinct system selections and settings. Their parallel existence is a product requirement, not an abandoned migration.
- **Glass grid versus Calm summaries/popup:** common model/control policy, intentionally different geometry and focus graphs. A universal layout/focus manager would add coupling.
- **Browser draft and TV saved state:** independent draft, Undo, revision conflict and unconfirmed-save handling protect user work. These are not competing authorities.
- **Frigate socket and 30-second reconciliation:** socket requests prompt refresh; polling recovers missed events. Profile duplicate refresh bursts before removing reconciliation.
- **Wall-clock labels, monotonic player progress and frame-clock bubble motion:** different time semantics. Do not unify them into a global per-frame state flow.
- **Shared slideshow frame state and HTTP disk cache:** one preserves decoded frames/fade, the other avoids network transfer. They store different representations for different reuse intervals.
- **HA and Frigate transports:** bearer origin checks versus certificate pinning/login cookies require separate client policy. A universal authenticated client is a credential-leak risk.

## Historical and dependency duplication

The original foreground idle infrastructure was removed by `37e3d5e`; no recommendation to remove it again is justified. Assistant compatibility models and old dock preference readers remain for saved data and version-1 transfer. Their names can mislead a reviewer, but deleting them would change migration behavior.

OkHttp is used consistently across network features; multiple client instances have distinct security/buffering policies. Conscrypt provides an Android-9-specific capability rather than duplicating TLS unnecessarily on every device. NanoHTTPD serves local HTTP; it does not duplicate OkHttp's outbound role. No second general image library was found. HAL-14 covers a small unused resource/permission review and production optimization verification, not an evidence-free dependency purge.

## Verification before removal

For each migrated consumer, compare old/new results for the same saved settings, missing data, hidden/reserved slots and visibility references; record resource counts and request counts before/after. Remove the old runtime producer only when every consumer has migrated. Preserve decoding/import compatibility separately from retired runtime orchestration. Reversible commits should change one ownership boundary at a time; no permanent dual-write or dual-refresh phase should remain.
